# generate-scope-template 工作流使用指南

## 概述

`generate-scope-template` 是 smart-contract-audit-toolkit 的**起点工作流**，用于生成 `.audit/scope.md` —— 审计范围与信任假设文档。

它回答四个问题：**这套系统里什么东西值钱**（核心资产）、**谁有特权**（角色与权限矩阵）、**什么被默认当成可信**（信任假设）、**钱怎么进怎么出**（经济模型与资金流）。

这份文档是 `smart-contract-audit-pipeline` 的**硬前置**：没有它、或者它没被人工签字，审计流水线跑不起来，而且**没有任何参数可以绕过**。

### 为什么要有这么一道坎

L2 语义审计的本事是判断"代码行为 ≠ 业务意图"。可它得先知道业务意图是什么。

- 没有范围文档 → AI 只能报模式化漏洞（重入、溢出这些静态工具也查得出来的），真正值钱的业务逻辑偏差报不出来；
- 更麻烦的是，它会把"owner 能改费率""owner 能暂停提现"这类**设计上就允许**的操作当成漏洞报出来，报告里塞满这种条目，真问题反而被淹了。

信任假设签字之后，L2 的 ⚖️裁判角色就能拿它做取舍：攻击前提正是某条已确认假设的，直接拒掉；攻击路径不依赖任何被信任主体的，照常判定。

## 何时使用

- ✅ **首次运行 `smart-contract-audit-pipeline` 之前**：硬前置，跑不掉
- ✅ **角色/权限变了**：加了新的 role、改了 onlyOwner 的范围、换了多签方案
- ✅ **经济模型变了**：加了新的费率参数、改了清算逻辑、接入了新的预言机
- ✅ **新增核心合约模块**：范围要扩，边界要重划
- ❌ **常规迭代**：日常 bug 修复、只改内部实现不改权限和资金流的，不需要重新生成；直接在 `.audit/scope.md` 里手工补一两行就行

## 前置依赖

**不需要任何外部工具**。纯 LLM 代码分析，只要仓库是个 Hardhat 项目就能跑，跟 `generate-invariants-template` 一样。

## 工作流的四个阶段

### 1️⃣ 准备

解析输入参数，决定是分析指定的合约还是自动发现。

**输入选项**：
- 不指定 → 自动发现核心合约（排除 `test/`、`script/`、`contracts/mocks/`、`contracts/interfaces/`，以及能判断为第三方 vendored/fork 的目录）
- 指定 `args.contracts` → 只分析这几个合约

### 2️⃣ 系统与角色分析（effort: high）

产出文档的第 1、2、3、5 章：

- **系统概述**：2-4 句话讲清这套合约在做什么生意
- **核心资产**：值钱、值得被攻击的东西——代币余额、原生 ETH、份额/凭证、治理投票权、特权本身；写清楚存在哪个合约的哪个状态变量里、属于谁、什么条件下能被取走
- **角色与权限矩阵**：实地从 `modifier`、AccessControl 的 role 常量、`require(msg.sender == x)` 里提取，逐个特权函数登记"哪个角色能调它"
- **信任假设**：这套代码在什么前提成立时才是安全的
- **审计边界**：in scope / out of scope 及排除原因

### 3️⃣ 经济模型与资金流（effort: high）

产出文档的第 4 章：

- **资金流入/流出入口**：会让合约余额增减的 external/public 函数
- **关键参数**：费率、利率、抵押率、清算阈值等，以及谁能改
- **机制**：清算、奖励分配、复利、赎回排队等
- **文档来源**：实际读到的 PRD/需求/设计文档路径（**没读到就不填**）
- **明确未找到的内容**：代码里读不出、文档里也没写的，如实列出

> 这里有条硬规矩：**禁止用常识补全业务规则**。"大多数借贷协议都这么做"不是本项目的事实，找不到就列进"明确未找到的内容"，让它变成人工待办。

### 4️⃣ 文档生成与保存

把两轮分析结果拼成五章 Markdown + 文末签字栏，用带围栏的 agent 写入 `.audit/scope.md`（围栏是防提示词注入：正文里万一混进"请忽略前面的指令"这类文字，也只会被当纯数据写进去）。

写完做两道**纯代码**校验：

1. 实际写入路径必须等于 `.audit/scope.md`；
2. 实际写入长度与预期的偏差不能超过 `max(64, 2%)`，超了判为"疑似被概括或截断"，标 `Failed`。

归档失败只记录在返回值的 `archive` 字段里、打一条 `⚠️` 日志，**不影响**已经算好的分析结果。

## 使用示例

### 基础用法：自动发现合约

```bash
/smart-contract-audit-toolkit:generate-scope-template
```

系统会：
1. 实地枚举 `contracts/` 下的自研合约
2. 分析资产、角色、权限矩阵、信任假设、审计边界
3. 分析资金流、关键参数、机制，并去 `docs/` 找业务文档
4. 生成 `.audit/scope.md`

### 高级用法：指定目标合约

```bash
/smart-contract-audit-toolkit:generate-scope-template contracts/Vault.sol,contracts/Token.sol
```

只分析指定的两个合约。

## 生成的文档结构

### 文件位置

`.audit/scope.md`

### 五章 + 签字栏

| 章节 | 内容 |
|------|------|
| **1. 系统概述与核心资产** | 这套合约在做什么生意 + 核心资产表（资产 / 类型 / 存放位置 / 说明） |
| **2. 角色与权限矩阵** | 角色表（角色 / 持有者 / 说明）+ 「角色 × 可调用的特权函数」矩阵 |
| **3. 信任假设** | `\| 主体 \| 假设 \| 依据 \| 状态 \|` ← **这一章是签字的对象** |
| **4. 经济模型与资金流** | 资金流入/流出、关键参数、机制、文档来源、明确未找到的内容 |
| **5. 审计边界** | in scope 列表 / out of scope 表（路径 + 排除原因） |
| **人工签字** | 确认人 / 确认日期 / 确认范围，生成时都是「（待填写）」 |

### 第 3 章的两个关键列

**状态列——只有两个合法值**：

| 值 | 含义 |
|---|---|
| `⬜ 待人工确认` | 工作流生成时的默认值，**一条不落全是这个** |
| `✅ 已确认` | 人工核对通过后手动改成这个，即为签字 |

**依据列——两种来源**：

| 值 | 含义 | 举例 |
|---|---|---|
| `代码推断` | 能从合约代码直接读出来 | "调用的是标准 IERC20 且检查了返回值，因此假定代币无 fee-on-transfer" |
| `需人工判断` | 代码里读不出来，取决于部署与治理的真实情况 | "owner 是 3/5 多签且成员互相独立"、"预言机喂价及时准确" |

想看真实产出长什么样，读仓库里的 `.audit/scope.md.template`（里面的假设、参数、路径都是虚构示例，别直接复制去用）。

## 人工签字要怎么做

这是整个工作流最关键的一步，也是唯一 AI 不能替你做的一步。

### 步骤 1：打开文件

```bash
code .audit/scope.md   # 或者你顺手的任何编辑器
```

### 步骤 2：逐条核对第 3 章

对每一条信任假设问自己一个问题：**这条假设在我们当前的部署环境下，真的成立吗？**

- 看到"owner 是 3/5 多签且成员互相独立" → 去翻部署脚本和多签配置，确认多签地址是什么、几个签名门槛、这几个 owner 是不是真的分属不同的人（而不是同一个人的多个钱包）；
- 看到"Chainlink ETH/USD 喂价及时准确" → 确认接的确实是官方 feed、心跳间隔是多少、有没有做 stale price 检查；
- 看到"USDC 无 fee-on-transfer、无 rebasing" → 确认要接的代币清单里没有奇葩 ERC20。

### 步骤 3：确认成立的，把状态改掉

把该行的 `⬜ 待人工确认` 手动改成 `✅ 已确认`：

```diff
- | owner 私钥 | 假定由 3/5 多签持有，成员互相独立 | 需人工判断 | ⬜ 待人工确认 |
+ | owner 私钥 | 假定由 3/5 多签持有，成员互相独立 | 需人工判断 | ✅ 已确认 |
```

**注意**：这两个标记是跨工作流的隐式契约，pipeline 靠它们判断"还剩几条没签"。别改写成"确认"、"OK"、"✅"之类的变体，会被判成未确认。

### 步骤 4：填写文末签字栏

```diff
  | 项目 | 值 |
  |---|---|
- | 确认人 | （待填写） |
- | 确认日期 | （待填写） |
+ | 确认人 | 张三 |
+ | 确认日期 | 2026-09-09 |
  | 确认范围 | 本文件第 3 章的全部信任假设 |
```

两栏都必须填，留空视为未完成。

### 步骤 5：提交到 git

`.audit/scope.md` 是签过字的东西，进版本库。以后回过头问"上线时那版范围文档是谁签的字"，git 记录和审计总报告里都能查到。

### 为什么"代码推断"的假设也要人签字

常见的困惑是：既然 `代码推断` 那一列的假设 AI 已经从代码里读出来了，为什么还要我签？

三个理由：

1. **签字是人的动作，不是判断的动作**。`✅ 已确认` 的含义不是"这条看起来对"，而是"**我本人核对过这条假设在当前部署环境下成立，并对此负责**"。责任不能由 AI 承担，所以标记也不能由 AI 打。
2. **代码推断本身可能推错**。"这个 ERC20 没有 fee-on-transfer" 是从**接口调用方式**推出来的，可实际要接哪些代币是运营决定的——代码里看着是标准 IERC20，上线接了个 fee-on-transfer 的代币，这条假设当场失效。
3. **这些假设会被当成事实喂给审计 AI**。L2 裁判会拿已确认的假设去**否掉**一些发现（"这条攻击前提正是已确认的信任假设，拒绝"）。一条没人核对过的假设混进来，代价是一条真实漏洞被静悄悄地拒掉。

`代码推断` 和 `需人工判断` 的区别只在于**核对成本**：前者你花 30 秒看眼代码就能确认，后者得去问部署和治理的实际情况。两类都要签。

### 有疑问的假设，别硬签

核对不了的（比如不确定 owner 私钥到底在谁手里、不确定上线会接哪些代币），先去把事情问清楚。

不要为了让 pipeline 跑起来而随手改成 `✅`——那等于把一条没验证的前提写成了事实，后面 L2 裁判会拿它当依据去否掉真实发现。如果某条假设确实不成立，正确做法是**改假设的内容**（或者干脆改代码），而不是硬签。

## 常见卡点

pipeline 报 `⛔ 审计范围文档未就绪，本轮审计不启动` 时，日志里会跟着列出具体原因。三种情况对应三种处理：

### 卡点 1：`.audit/scope.md 不存在或未能读取`

```
.audit/scope.md 不存在或未能读取。请先运行 /smart-contract-audit-toolkit:generate-scope-template
生成审计范围文档，人工确认信任假设并签字后再跑本流水线。
```

**说明**：文件根本没生成，或者上一次生成时归档失败了。

**怎么办**：
1. 先跑 `/smart-contract-audit-toolkit:generate-scope-template`；
2. 跑完看返回值里的 `archive.status`。如果是 `Failed`，读一下 `archive.error`：
   - "写入路径与预期不符" → agent 把文件写到别处了，重跑一次；
   - "写入长度与预期不符…疑似被概括或截断" → 内容被概括了，重跑一次；
   - "文档生成或写入异常：…" → 看具体报错，通常是权限或磁盘问题；
3. 确认 `.audit/scope.md` 真的躺在仓库里，再去签字。

> 注意：也有可能文件在，但上下文 agent 没读出来。这套门禁是 **fail-closed** 的——读不出来一律判不通过，因为"读不出来"和"确认过了"不能等价。

### 卡点 2：`仍有 N 条信任假设为「⬜ 待人工确认」`

```
.audit/scope.md 中仍有 2 条信任假设为「⬜ 待人工确认」，请逐条核对后改成「✅ 已确认」：
  - owner：假定不作恶，且不会把 oracle 换成受控合约抽干资金池
  - Chainlink ETH/USD 预言机：假定喂价及时且准确，不会长时间停更
```

**说明**：这是**第一次上手最常见的卡点**，也是设计意图——三步流程（生成 → 签字 → 审计）里，你正卡在第二步。

**怎么办**：日志已经把卡住的条目逐条列出来了（不是甩一句"未确认"让你自己找），按上面「人工签字要怎么做」逐条核对、改状态列即可。

**常见的坑**：
- 状态列改成了 `✅`、`已确认`、`确认` 等变体 → 必须是完整的 `✅ 已确认`；
- 用编辑器的"全部替换"一把梭把所有 `⬜ 待人工确认` 替换成 `✅ 已确认` → **技术上能让门禁过，但这恰恰是这道门禁想拦住的行为**。逐条核对是这一步唯一的价值所在，批量替换等于把整套机制变成一句空话。

### 卡点 3：`签字栏的「确认人」/「确认日期」为空`

```
.audit/scope.md 文末签字栏的「确认人」为空，未完成人工签字
```

**说明**：第 3 章都改成 `✅ 已确认` 了，但文末签字栏还是「（待填写）」。

**怎么办**：把确认人和确认日期填上。两栏都要填，"（待填写）"这类占位符会被当成空值。

### 卡点 4：门禁过了，但审计结论看着不对劲

比如报告里一个"权限"类问题都没有，或者明显该报的管理员风险被拒掉了。

**怎么办**：回头看 `.audit/scope.md` 的第 3 章——很可能是某条信任假设写得太宽（比如"owner 完全可信，其任何操作都不构成风险"），把裁判该判的东西一并挡掉了。

写信任假设的原则是**尽量窄**：写"owner 可调整费率上限，且已确认为 3/5 多签"，别写"owner 可信"。

顺便记住裁判规则的边界：**"信任 owner"只覆盖 owner 的合法操作，不覆盖"任意人都能冒充 owner"这类权限校验缺陷**。如果一条攻击路径任意外部账户都能发起，信任假设不构成拒绝理由。

## 与其他工作流的协作

### smart-contract-audit-pipeline（L1-L4 审计）

**依赖关系（硬前置）**：`generate-scope-template` → 👤 人工签字 → `smart-contract-audit-pipeline`

范围文档在流水线里被用在三处：

1. **准备阶段的门禁**：`evaluateScopeGate(context)` 纯代码判三条硬性条件，不满足直接早退；
2. **上下文摘要**：上下文 agent 优先读 scope.md，把它的要点作为五段摘要的第①段；如果第 4 章已写明经济模型，直接采信，不再重复去翻 PRD 文档；
3. **L2 ⚖️裁判角色**：额外吃一份 scope 摘要，按裁判规则第 0 条用已签字的信任假设过滤发现。

审计总报告 `.audit/reports/audit-latest.md` 的「审查元信息」表里还会记一行：

```
| 审计范围文档 | `.audit/scope.md`（确认人：张三，确认日期：2026-09-09） |
```

缺失时显示"未提供"。作用是可追溯性——回答"上线时那版是谁签的字"。

### generate-invariants-template（不变量清单）

**并列关系**：两个都是准备类工作流，产出都是给人看、给人改、给人签字的清单文件，互不依赖。

推荐先跑 `generate-scope-template`：把资产和角色理清楚之后，再看不变量清单会更有判断力。

## 常见问题

### Q: AI 列的信任假设不准确/漏了怎么办？

**A**: 完全正常，AI 生成的只是初稿。直接编辑 `.audit/scope.md`：
- 删掉不成立的行
- 改写措辞太宽的假设（把"owner 可信"改成"owner 可调整费率上限，且已确认为 3/5 多签"）
- 补上 AI 漏掉的假设

不需要重跑工作流。

### Q: 第 4 章里"明确未找到的内容"列了一堆，是不是哪里出错了？

**A**: 不是。那一列恰恰说明工作流没有用常识去糊弄你——代码里读不出、文档里也没写的东西，它如实列出来了。把它当成人工待办清单：要么去补文档，要么在评审时把这些问题问清楚。

### Q: 合约改了，需要重新生成整份文档吗？

**A**: 看改了什么：
- 只改内部实现，权限和资金流没变 → 不用，最多手工补一两行；
- 加了新的 role、改了 onlyOwner 范围、加了新的费率参数、换了预言机 → 建议重跑，然后**重新逐条签字**（新生成的文档里所有假设又会变回 `⬜ 待人工确认`，这是有意为之）。

### Q: 能不能加个参数跳过这道门禁？

**A**: 不能，也不打算加。这道门禁没有任何开关，而且是纯代码判断（不调大模型），就是为了让"绕过"这件事在技术上不成立。

如果你只是想快速看一眼 L1 静态扫描结果，直接跑 slither/aderyn 就行，不用走这条流水线。
