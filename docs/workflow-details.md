# Smart Contract Audit Toolkit - 工作流详细说明

这份文档用大白话讲清楚五个工作流到底是怎么跑的：每一步干什么、用什么工具、为什么要这么做、最后能拿到什么。

按**执行顺序**排列：
1. 📐 先划清审计范围、把信任假设摆到台面上（**跑审计流水线的硬前置**）
2. 📋 再生成一份不变量清单（项目刚起步时的准备工作）
3. ⭐ 抽样式：Fuzz 随机测试
4. ⭐⭐⭐ 启发式：语义审计 + 拿 PoC 实锤
5. ⭐⭐⭐⭐⭐ 穷尽式：形式化验证

---

## 0. generate-scope-template（生成审计范围与信任假设文档）

### 概述

**这是干嘛的**：把核心合约扫一遍，搞清楚四件事——**有什么值钱的东西**（核心资产）、**谁有特权**（角色与权限矩阵）、**什么被默认当成可信的**（信任假设）、**钱怎么进怎么出**（经济模型与资金流），生成一份 `.audit/scope.md`。

**为什么非要有它**：L2 语义审计的本事是判断"代码行为 ≠ 业务意图"，可它得先知道业务意图是什么。没有这份文档，AI 只能报模式化漏洞（重入、溢出这些静态工具也能查的），报不出业务逻辑偏差；更麻烦的是，它会把"owner 能改费率"这种设计上就允许的操作当成漏洞报出来，把报告的信噪比拉垮。

**能证明到什么程度**：谈不上证明，它是给后面所有审计打地基的上下文文件。

**跑一次贵不贵**：很便宜，纯 LLM 分析，不用装任何外部工具。

**大概要多久**：一般 3-8 分钟（两个分析 agent 都用 high effort，读得比较细）。

**有一点必须说清楚**：它生成的信任假设**一律是「⬜ 待人工确认」**，包括那些能从代码直接读出来的。因为"签字"是人的动作，AI 不代签。签完字之前，`smart-contract-audit-pipeline` 跑不起来。

---

### 流程图

```
准备：解析 args.contracts
    │
    ▼
系统与角色分析（effort: high）
  - 系统概述 + 核心资产
  - 角色 + 权限矩阵（从 modifier / AccessControl / require 实地提取）
  - 信任假设（每条标 code-inferred 或 needs-human）
  - 审计边界 in scope / out of scope
    │
    ▼
经济模型与资金流分析（effort: high）
  - 资金流入/流出入口
  - 关键参数 + 谁能改
  - 机制（清算/复利/奖励分配…）
  - 文档来源 + 明确未找到的内容
    │
    ▼
拼装 Markdown（五章 + 人工签字栏）
  信任假设状态列一律填「⬜ 待人工确认」
    │
    ▼
带围栏的 Agent 写入 .audit/scope.md
    │
    ▼
纯代码校验：路径 == .audit/scope.md？长度偏差 ≤ max(64, 2%)？
  ├─ 否 → archive.status = Failed（分析结果照样返回）
  └─ 是 → archive.status = Written
                    │
                    ▼
   返回 system / economics / pendingAssumptionCount / archive
                    │
                    ▼
        👤 人工逐条签字（这一步 AI 不做）
                    │
                    ▼
        smart-contract-audit-pipeline 才会放行
```

### 工作流程与步骤

#### **准备阶段**

| 步骤 | 操作 | 工具 | 说明 | 为什么需要 |
|------|------|------|------|------|
| 0.1 | 解析输入参数 | 无 | 看看你有没有用 `args.contracts` 指定要分析的合约；没指定就自动去发现（排除 test/、script/、mocks/、interfaces/ 以及能判断为第三方 vendored/fork 的目录） | 第一次做全量范围梳理要能自动铺开；后面只是加了个新模块、想补一小块范围时，又不用把全仓库重新分析一遍 |

---

#### **系统与角色分析阶段**

| 步骤 | 操作 | 工具 | 说明 | 为什么需要 |
|------|------|------|------|------|
| 1.1 | 系统概述 | **Claude LLM** | 2-4 句话讲清这套合约在做什么生意（借贷/AMM/质押/NFT 市场…） | 后面每一条判断都得挂在"这门生意本来该怎么运作"上；连在做什么都说不清，"业务逻辑偏差"就无从谈起 |
| 1.2 | 识别核心资产 | **Claude LLM** | 找出系统里有价值、值得被攻击的东西：代币余额、原生 ETH、份额/凭证、治理投票权、特权本身。写清楚它存在哪个合约的哪个状态变量里、属于谁、什么条件下能被取走 | 审计的本质是"防止不该拿走的人拿走东西"；资产列表就是在回答"攻击者到底图什么"，没有这张表，攻击面分析只能靠猜 |
| 1.3 | 提取角色与权限矩阵 | **Claude LLM** | 实地从 `modifier`、AccessControl 的 role 常量、`require(msg.sender == x)` 里提取角色，再逐个特权函数登记"哪个角色能调它"，并标出是否影响资金、是否有时锁、是否可暂停 | 必须实地读代码提取，不能凭常识预设"应该有个 owner"；权限矩阵是后面判断"这个操作算不算越权"的唯一标尺 |
| 1.4 | 列出信任假设 | **Claude LLM** | 这一步是整个工作流最重要的产出：列出"这套代码在什么前提成立时才是安全的"，每条标注依据：<br/>- **code-inferred**（代码推断）：能从代码直接读出，比如"调用的是标准 IERC20 且检查了返回值，因此假定代币无 fee-on-transfer"<br/>- **needs-human**（需人工判断）：代码里读不出来，取决于部署和治理的真实情况，比如"owner 是 3/5 多签且成员互相独立"、"预言机喂价及时准确" | 宁可多列几条 needs-human，也不能把猜测标成 code-inferred——这些假设会被喂给审计 AI 当作事实，标错会直接污染整轮审计结论 |
| 1.5 | 划定审计边界 | **Claude LLM** | 给出 in scope 建议列表，以及 out of scope 及其原因（第三方 vendored 代码只查"我们怎么调用它"，不审源码本身） | 边界不写清楚，审计报告会被"这个文件为什么没审"这类问题反复挑战；写清楚了，"没审"就是一个有据可查的决定，而不是疏漏 |

**系统与角色分析产出**：overview / assets / roles / permissions / trustAssumptions / inScope / outOfScope

---

#### **经济模型与资金流阶段**

| 步骤 | 操作 | 工具 | 说明 | 为什么需要 |
|------|------|------|------|------|
| 2.1 | 梳理资金流入/流出入口 | **Claude LLM** | 逐个列出会让合约余额增加或减少的 external/public 函数（deposit/withdraw/borrow/repay/claim/liquidate 等），写明函数签名与所属合约 | 资金进出口就是攻击者最终要走的那扇门；把门都登记在册，后面审计才能一扇一扇地问"这扇门的锁靠谱吗" |
| 2.2 | 记录关键参数 | **Claude LLM** | 费率、利率、抵押率、清算阈值、上限额度等，写明代码里的默认/初始化值，以及谁能改它 | "谁能改这个参数"直接决定了一条信任假设成不成立；参数和权限对不上的地方，往往就是漏洞藏身的位置 |
| 2.3 | 说明业务机制 | **Claude LLM** | 清算、奖励分配、复利、赎回排队等机制，各用一两句话说清触发条件与收益归属 | 这类机制的语义静态工具完全看不懂，只能靠文字描述交接给 L2；描述不清楚，L2 就只能当成普通转账逻辑草草看过 |
| 2.4 | 查找文档来源 | **Claude LLM** | 在 `docs/` 或仓库根目录找 PRD/需求/设计类文档，重点看资金流转/利率/清算/额度相关章节。**实际读到了才把路径填进 docSources** | 业务意图的权威出处是文档不是代码；但没读到就绝对不能编路径，否则后面的人会顺着一个不存在的引用去找依据 |
| 2.5 | 如实记录"没找到的" | **Claude LLM** | 凡是代码里读不出、文档里也没写的（典型如"利率曲线拐点为什么取 80% 利用率"），如实列进 notFound | 禁止用常识补全业务规则——"大多数借贷协议都这么做"不是本项目的事实。列进 notFound 之后，这一条就变成了一个人工待办，而不是一个被悄悄糊弄过去的空白 |

**经济模型产出**：fundsIn / fundsOut / parameters / mechanisms / docSources / notFound

---

#### **文档生成与保存阶段**

| 步骤 | 操作 | 工具 | 说明 | 为什么需要 |
|------|------|------|------|------|
| 3.1 | 拼装 Markdown | 无 | 把两轮分析的结构化结果转成五章文档 + 文末人工签字栏；**信任假设的状态列一律填「⬜ 待人工确认」**，签字栏填「（待填写）」 | 一堆 JSON 人是没法逐条核对、更没法签字的；转成表格之后，工程师直接在表格里改状态列就行。状态列一律填 ⬜ 是硬规则：AI 不给自己的推断盖章 |
| 3.2 | 写入磁盘 | **Claude LLM** | 用 agent 把文件写到 `.audit/scope.md`，正文用围栏（fence）跟指令隔开 | 围栏的作用是防提示词注入：文档正文里万一混进"请忽略前面的指令"这类文字，也只会被当成纯数据写进去，不会被当成命令执行。和其他几个工作流的归档是同一套做法 |
| 3.3 | 校验写入 | 无 | 两道纯代码校验：<br/>① 实际写入路径必须等于 `.audit/scope.md`；<br/>② 实际写入长度与预期的偏差不能超过 `max(64, 2%)`，超了就判为"疑似被概括或截断"，标 Failed | LLM 说"我写成功了"不代表真写成功了——路径可能写错、内容可能被它顺手概括掉。靠纯代码核对路径和长度，是防"AI 自己汇报不靠谱"的最后一道保险 |

**归档失败会怎样**：只把失败状态和原因记在返回值的 `archive` 字段里、打一条 `⚠️` 日志，**不影响** `system` / `economics` 这两块已经算好的分析结果——总不能因为最后写文件失败，就把前面几分钟的分析成果全扔了。

### 最终产出物

```
.audit/
└── scope.md                            # 审计范围与信任假设文档
    ├── 1. 系统概述与核心资产
    ├── 2. 角色与权限矩阵（角色表 + 「角色 × 可调用的特权函数」矩阵）
    ├── 3. 信任假设            ← | 主体 | 假设 | 依据 | 状态 |
    │      依据：代码推断 / 需人工判断
    │      状态：⬜ 待人工确认 / ✅ 已确认（生成时一律 ⬜）
    ├── 4. 经济模型与资金流（流入流出、关键参数、机制、文档来源、明确未找到的内容）
    ├── 5. 审计边界（in scope / out of scope）
    └── 人工签字（确认人 / 确认日期 / 确认范围，生成时为「（待填写）」）
```

返回值：`{ system, economics, pendingAssumptionCount, archive }`，其中 `archive` 是 `{ status, path, error?, writtenLength? }`。

想先看看真实产出长什么样，仓库里有一份示例模板 `.audit/scope.md.template`（里面的假设、参数、路径都是虚构的，别直接复制去用）。

### 使用建议

- **什么时候跑**：第一次跑 `smart-contract-audit-pipeline` 之前（硬前置，绕不过去）；或者合约的角色/权限/经济模型有变化之后，重新过一遍
- **跑完必须做的事**：打开 `.audit/scope.md`，**逐条**核对第 3 章的信任假设，确认成立的把状态从「⬜ 待人工确认」改成「✅ 已确认」，然后填写文末签字栏的确认人和确认日期。这一步没做，pipeline 会在准备阶段直接早退
- **代码推断的假设也要签字**：`代码推断` 只是说"这条能从代码读出来，核对成本低"，不是说"不用核对"。签字的含义是"我本人核对过这条假设在当前部署环境下成立，并对此负责"
- **有疑问的假设别硬签**：核对不了的（比如不确定 owner 私钥到底在谁手里），先去把事情问清楚，别为了让 pipeline 跑起来而随手改成 ✅——那等于把一条没验证的前提写成了事实，后面 L2 裁判会拿它当依据去否掉真实发现
- **文档要进 git**：`.audit/scope.md` 是签过字的东西，提交到版本库里，以后能查"上线时那版是谁签的"
- **详细的签字操作与常见卡点**：见 [generate-scope-guide.md](./generate-scope-guide.md)

## 1. generate-invariants-template（生成不变量清单）

### 概述

**这是干嘛的**：项目刚起步的时候，自动把核心合约扫一遍，找出"系统必须一直成立的规矩"（也就是不变量），生成一份 `.audit/invariants.md` 清单文件。

**能证明到什么程度**：谈不上证明，它就是个辅助工具，帮你先把该盯防的点列出来。

**跑一次贵不贵**：很便宜，只是让 LLM 分析一下，不用装任何外部工具。

**大概要多久**：一般 2-5 分钟。

---

### 流程图

```
准备：解析 args.contracts
    │
    ▼
合约分析：发现核心合约（排除 test/mocks 等）
    │
    ▼
发现到合约？
  ├─ 否 → 结束：返回错误，无可分析的合约
  └─ 是
        │
        ▼
不变量识别：每个合约识别 3-5 条关键性质
        │
        ▼
生成 Markdown 清单
        │
        ▼
Agent 写入 .audit/invariants.md
        │
        ▼
写入路径校验通过？
  ├─ 否 → archive.status = Failed ─┐
  └─ 是 → archive.status = Written ┤
                                   ▼
                 返回 contracts / invariants / archive
```

---

### 工作流程与步骤

#### **准备阶段**
| 步骤 | 操作 | 工具 | 说明 | 为什么需要 |
|------|------|------|------|------|
| 0.1 | 解析输入参数 | 无 | 看看你有没有指定要分析的合约列表；没指定就自动去发现 | 这样项目刚起步想全量生成一遍清单可以，合约后面改动大了只想补几条不变量也行，不用每次都手动把文件名一个个列出来 |

---

#### **合约分析阶段**

| 步骤 | 操作 | 工具 | 说明 | 为什么需要 |
|------|------|------|------|------|
| 1.1 | 发现核心合约 | **Claude LLM** | 把 `contracts/` 目录翻一遍，找出核心合约（test/、mocks/ 这些不算）<br/>对每个合约记下来：<br/>- 叫什么名、在哪个文件、是干嘛的<br/>- 核心状态变量有哪些<br/>- 关键的 public/external 方法有哪些 | 不变量总得挂在具体的状态变量和方法上才有意义；提前把测试脚手架和纯工具库排除掉，省得把不相关的代码也当成要保证安全的对象来分析，白花分析成本还添乱 |
| 1.2 | 合约特征提取 | **Claude LLM** | 为下一步识别不变量准备好必要的代码信息 | 下一步生成的检验函数名（`invariant_*`）和描述都得对应到真实存在的状态变量/方法名上；这一步不做好，下一步就只能瞎编变量名，生成出来的清单没法直接对上代码 |

**合约分析产出**：
- 核心合约列表（name, path, description, primaryStateVars, publicFunctions）

---

#### **不变量识别阶段**

| 步骤 | 操作 | 工具 | 说明 | 为什么需要 |
|------|------|------|------|------|
| 2.1 | 识别关键性质 | **Claude LLM** | 给每个合约挑 3-5 条关键的系统规矩，分成四类：<br/>- **conservation**（守恒型）：某种资源/总量必须守恒<br/>  比如：总代币供应量 = sum(balances)<br/>- **state-consistency**（状态一致型）：不同状态变量之间得对得上<br/>  比如：nonce 只能越来越大<br/>- **invariant-property**（不变性质）：某个状态属性必须一直成立<br/>  比如：用户余额 ≥ 0<br/>- **boundary**（边界条件）：允许的最大/最小值<br/>  比如：手续费不能超过转账额度 | 用这四类硬性框架逼自己做地毯式排查，不然很容易只想到"余额不能是负数"这种单一角度，把总量守恒这种更常见的资金安全大坑漏掉 |
| 2.2 | 分配 ID 与设计检验方式 | **Claude LLM** | 给每条不变量：<br/>- 编个号（INV-01, INV-02, ...）<br/>- 建议一个检验函数名（照 echidna 的规矩：invariant_*）<br/>- 说说这条规矩背后的风险，以及打算怎么 fuzz | 不变量要是落不到一个具体、能跑起来的 echidna 风格函数名上，下游 `invariant-fuzz-campaign` 就没法自动帮你搭测试装置，清单就只能停留在纸面上，没法真正拿去验证 |
| 2.3 | 质量检查 | **Claude LLM** | 确保每条不变量都满足：<br/>- ✅ 具体到能直接写成 Solidity 的 assert()<br/>- ✅ 重要到一旦违反就是大事<br/>- ✅ 独立，不跟别的不变量炒冷饭<br/>- ❌ 别太琐碎，不能是自己证自己的废话 | 把写不成 assert 的、或者太琐碎自证的条目筛掉；清单里一堆没用的条目，会把后面 fuzz 报告的信噪比拉得很低，真正的问题反而被埋没在噪音里 |

**不变量识别产出**：
- 不变量清单（id, description, category, contract, testEntry, rationale, suggestedFuzzStrategy）

---

#### **清单生成与保存阶段**

| 步骤 | 操作 | 工具 | 说明 | 为什么需要 |
|------|------|------|------|------|
| 3.1 | 生成 Markdown 清单 | 无 | 把结构化数据转成 `.audit/invariants.md` 的表格格式 | 一堆结构化 JSON 人是看不下去的，也不好协作改；转成表格之后，工程师直接在表格里增删改就行，不用管底层数据长什么样 |
| 3.2 | 写入磁盘 | **Claude LLM** | 用 agent 安全隔离地把文件写到磁盘上 | 让"生成内容"和"写文件"这两步在同一个受控的环境里完成，中间用围栏（fence）把清单正文和"写入指令"隔开，防止清单里万一混进什么奇怪文字被误当成指令去执行 |
| 3.3 | 校验写入 | 无 | 确认文件路径写对了、内容没被动过手脚 | LLM 说"我写成功了"不代表真写成功了——路径可能写错、内容可能被截断或者被它自己概括了；靠纯代码去核对路径和长度，这是防"AI 自己汇报不靠谱"的最后一道保险 |

---

### 最终产出物

```
.audit/
└── invariants.md                    # 不变量清单（人工维护的输入文件）
    ├── 表格格式，每行一个不变量
    ├── 字段：ID | 合约 | 描述 | 类别 | 检验方式 | 状态 | 备注
    └── 用户可直接编辑，加入新不变量或调整已有项目
```

### 使用建议

- **什么时候跑**：项目刚起步、第一次跑 `invariant-fuzz-campaign` 之前；或者合约架构大改之后，重新过一遍
- **生成的东西要不要信**：AI 列出来的不变量只能当参考，得让**懂业务的工程师亲自过一遍**，重点看：
  - 有没有漏掉什么关键规矩
  - 建议的检验函数是不是真能用 Solidity 简单写出来
  - 不变量的描述说得准不准
- **以后怎么维护**：之后想改 `invariants.md`，直接改表格就行，不用重新跑这个工作流

## 2. invariant-fuzz-campaign（不变量深度模糊测试）

### 概述

**这是干嘛的**：拿智能合约的"核心不变量"（系统永远得成立的那些规矩）做长时间随机测试，专门找那种"组合型"漏洞——得靠好几笔交易连续操作才会暴露出来的状态错乱，单次调用根本看不出来。

**能证明到什么程度**：⭐ 低——本质是抽样式的随机测试，跑不到的地方就是跑不到，可能有漏网之鱼。

**跑一次贵不贵**：低到中等，看你 fuzz 跑几轮、给多少时间。

**大概要多久**：一般每轮 5-20 分钟，这个是可以调的。

### 工作流程与步骤

#### **准备阶段**
| 步骤 | 操作 | 工具 | 说明 | 为什么需要 |
|------|------|------|------|------|
| 1.1 | 加载不变量清单 | 无 | 把 `.audit/invariants.md` 读进来，解析出里面所有不变量的定义 | 这个工作流不负责发现新东西，只负责验证已经被人审核过的不变量——所有要测的东西都来自这份权威清单，不是 AI 临时拍脑袋想出来的 |
| 1.2 | 过滤有效不变量 | 无 | 把标了 `skip: true` 的不变量踢出去，不测它们 | 有些不变量可能因为装置暂时搭不安全、或者依赖还没就绪，被人工标了跳过；照单全跑的话会在装置那一步反复失败、白白浪费时间，尊重人工的标记能让这一轮 fuzz 专心测真正测得动的目标 |
| 1.3 | 初始化测试环境 | **Hardhat** | 把合约编译一遍，顺便生成合约 ABI | Echidna/Medusa 得对着真实字节码跑，装置里部署的必须是"真合约"而不是假想的接口；不先编译一遍，都不知道合约能不能正常构建，也拿不到装置需要的 ABI |
| 1.4 | 准备 Fuzz 装置框架 | 无 | 给每个不变量生成一套 Echidna/Medusa 都认的测试装置（harness） | Fuzz 引擎自己只会瞎调用，它根本不知道"怎样才算违反业务规矩"；得先把每条不变量翻译成 `invariant_*()` 这种函数，引擎才能在每次状态变化后自动帮你 check |

---

#### **装置生成阶段**

| 步骤 | 操作 | 工具 | 说明 | 为什么需要 |
|------|------|------|------|------|
| 2.1 | 工具可用性检测 | `echidna` 或 `medusa` | 看看 echidna 或 medusa 装没装，没装就自动试着装一下 | 别等装置和用例都搭好了才发现工具根本装不上，那前面全白干；工具真装不上就老实说"不可用"，绝不能装模作样伪造 fuzz 结果，这是这套工具链的底线 |
| 2.2 | 为每个不变量生成装置 | **Claude LLM** | 把不变量翻译成 Solidity 代码里的一个 `invariant_*()` 函数：<br/><br/>**举个例子**：<br/>```solidity<br/>// 不变量：总供应量 = sum(balances)<br/>function invariant_total_supply() public {<br/>  assert(token.totalSupply() == sumAllBalances());<br/>}<br/>```<br/><br/>装置长这样：<br/>- 每条不变量对应一个独立的 invariant 函数<br/>- 这个函数会在每次状态变化后被 fuzzer 自动调用<br/>- 只要 assert 失败，就说明抓到了一条违反不变量的调用序列 | 不变量清单里写的是大白话描述，Fuzz 引擎只看得懂 Solidity 断言函数；这一步就是把"应该一直成立的规矩"翻译成引擎能反复自动检查的可执行代码 |
| 2.3 | 生成 Echidna 装置（如适用） | **Claude LLM** | 生成 `echidna-harness.sol`，包含：<br/>- Solidity 代码<br/>- `invariant_*()` 函数<br/>- 必要的状态追踪和辅助函数<br/>- Echidna 配置注释 | 两个引擎的实现路子不一样，各自能摸到的执行路径也不完全重合；分别生成配套装置，是为了让两个引擎都能真跑起来，而不是共用一份可能只对得上其中一个的配置 |
| 2.4 | 生成 Medusa 装置（如适用） | **Claude LLM** | 生成 `medusa-harness.sol`，Medusa 认的格式：<br/>- 跟 Echidna 差不多的 invariant 函数<br/>- 额外的 property 定义<br/>- Medusa 专用的钩子函数 | 跟 2.3 一个道理——两个引擎互相补位，一个漏掉的路径另一个说不定能覆盖到，降低漏检的概率 |
| 2.5 | 装置验证 | **Hardhat** | 把生成出来的装置代码编译一遍，看有没有语法错误 | 装置代码也是 LLM 写出来的，得在真正开始长跑（几分钟到几十分钟）之前先确认它能编译过，不然时间预算全砸在一个根本跑不起来的装置上 |

**装置生成产出**：
- `echidna-harness.sol` - Echidna 格式的测试装置
- `medusa-harness.sol` - Medusa 格式的测试装置
- 配置文件（echidna.yaml / medusa.json）

---

#### **Fuzz 长跑阶段**

| 步骤 | 操作 | 工具 | 说明 | 为什么需要 |
|------|------|------|------|------|
| 3.1 | 启动 Echidna 长跑（如启用） | **Echidna** | 拿装置跑 Echidna：<br/>- **喂给它**：装置代码 + 不变量函数<br/>- **它干什么**：随机拼交易序列，调合约的函数，边跑边检查不变量<br/>- **给多少时间**：由 `minutesPerRound` 定（默认 5 分钟）<br/>- **跑几轮**：由 `roundsPerEngine` 定（默认 3 轮）<br/>- **特点**：<br/>  - 用覆盖率来引导怎么随机（coverage-guided fuzzing）<br/>  - corpus（探索过的输入）跨轮留着接着用<br/>  - 一旦发现某条序列打破了不变量，立刻停下来记反例 | 覆盖率引导的长时间随机测试，是抓"好几笔交易连起来才暴露的状态错乱"（组合型漏洞）最管用的办法——这类漏洞不是单次调用能测出来的，人工审计或者静态扫描很难系统性地把它们都挖出来 |
| 3.2 | Echidna 结果收集 | **Echidna** | 每轮每条不变量都记一下：<br/>- 状态：`Passed`、`Falsified`、`Timeout`<br/>- 测试调用了多少次<br/>- 如果是 Falsified，把反例交易序列记下来<br/>- 如果是 Timeout，说明这轮时间不够没跑完 | 得把工具跑出来的状态和反例都结构化记下来，后面归档那一步才能判断 overallStatus、生成回归测试 |
| 3.3 | 启动 Medusa 长跑（如启用） | **Medusa** | 拿装置跑 Medusa：<br/>- 跟 Echidna 类似，但实现不一样<br/>- 有可能挖到 Echidna 没挖到的反例<br/>- 时间预算和轮数都一样 | 双引擎交叉验证：实现不一样，探路的策略也不一样，Medusa 有机会挖到 Echidna 没覆盖到的反例，提高发现漏洞的概率 |
| 3.4 | Medusa 结果收集 | **Medusa** | 记录格式跟 Echidna 一样 | 跟 3.2 一样，给归档阶段提供结构化的输入 |
| 3.5 | 反例永久保存 | 无 | 把所有 Falsified 的反例交易序列存进 `.audit/regression/`：<br/>```<br/>.audit/regression/<br/>├── INV-01_falsified_round1.tx<br/>├── INV-02_falsified_round2.tx<br/>└── ...<br/>``` | 规矩一旦被打破，就得把能复现的调用序列固化成回归测试，不然以后改代码的时候，这个漏洞被不小心又引入了都没人知道 |
| 3.6 | Corpus 更新 | **Echidna** / **Medusa** | 把最新的 corpus（探索过的输入集合）留着，供下次运行接着用 | 覆盖率是一轮一轮攒起来的；把探索过的输入语料留着，下一轮/下次运行接着用，能让"跑得越久覆盖率越高"，不用每次都从零开始白费算力 |

**Fuzz 长跑产出**：
- 每个不变量 × 每个引擎 × 每轮 = 一条结果记录
- 若有 Falsified：附带反例交易序列
- Corpus 文件（供后续增量 fuzz 复用）

---

#### **结果归档阶段**

| 步骤 | 操作 | 工具 | 说明 | 为什么需要 |
|------|------|------|------|------|
| 4.1 | 结果汇总与分类 | 无 | 把所有 fuzz 结果收集起来：<br/>- 按不变量分组<br/>- 按引擎分组<br/>- 按轮次分组 | 一条 fuzz 结果只对应一个不变量+一个引擎+一轮，得先结构化汇总起来，报告里才能给出"这条不变量到底有没有被证伪"这种整体结论 |
| 4.2 | 阻断项识别 | 无 | 把所有 Falsified 的结果挑出来，这些就是**阻断项**：<br/>- 只要出现 Falsified 就说明挖到了组合型漏洞<br/>- 必须进一步分析和修复 | Falsified 意味着真的挖到了违反系统规矩的调用序列，这是优先级最高的问题；得让这种结果在报告里显眼地摆出来，别被一堆 Passed 结果淹没了让人看漏 |
| 4.3 | 生成 Fuzz 报告 | 无 | 生成 `.audit/reports/invariant-fuzz-latest.md`，里面有：<br/>- **概览** - 跑的参数（引擎、轮数、时间预算）<br/>- **统计** - 一共多少不变量、通过/失败各多少<br/>- **阻断项** - 所有 Falsified 的不变量和反例<br/>- **逐条明细** - 每条不变量按引擎分别展开 | 长跑结果只躺在日志里没什么用，得整理成人能看懂的报告，让人工复核的时候能一眼看出"这轮哪些不变量过了、哪些被跳过（不代表安全）、哪些是真被打破了" |
| 4.4 | 报告写入磁盘 | 无 | 覆盖写入 `.audit/reports/invariant-fuzz-latest.md` | 固定路径覆盖写入，保证每次都在同一个地方能找到最新结果，不用每次都去翻带时间戳的文件名 |

## 3. smart-contract-audit-pipeline（四层审计流水线）

### 概述

**这是干嘛的**：对 Hardhat 智能合约项目做一次全面、多角度的安全审计，从"死板但可靠"的静态扫描一路做到人工复核，最后出一份完整的审计报告。

**能证明到什么程度**：⭐⭐⭐ 中等——靠经验和推理去审计，加上对部分发现做实锤验证（PoC）。

**跑一次贵不贵**：中等，看合约数量和代码量。

**大概要多久**：一般 5-15 分钟，L1 到 L4 全算在内。

**⚠️ 硬前置（必须先看）**：本流水线在「准备」阶段、L1 之前会先跑一道范围文档门禁 `evaluateScopeGate(context)`（**纯函数，不调大模型**，避免让 AI 给自己的前置条件打分）。三条硬性条件，**任一不满足就直接早退**，返回 `{ error: '审计范围文档未就绪', scopeGate }`：

1. `.audit/scope.md` 存在且可读；
2. 第 3 章「信任假设」没有剩余的「⬜ 待人工确认」；
3. 文末签字栏的**确认人**与**确认日期**都非空。

**没有任何参数能绕过**（不存在 `skipScopeCheck` 这类开关），而且是 fail-closed 的：上下文 agent 返回空值或结构异常时一律判为不通过——"读不出来"和"确认过了"绝不能等价，否则这道前置形同虚设。早退时的日志会**逐条列出**卡在哪几条未确认假设，而不是甩一句"未确认"让你自己找。

所以标准使用顺序是三步：`generate-scope-template` 生成 → **人工逐条签字** → 才能跑审计。第一次上手一定会卡在中间这步，这是设计意图，不是 bug。

| 1.1 | 加载审计上下文 | **Claude LLM** | 读 `.audit/scope.md`（**优先读它**）、`.audit/invariants.md`、`.audit/false-positives.md`、`.audit/exemptions.md`，返回**结构化 JSON**（`CONTEXT_SCHEMA`）：<br/>- `scopeExists`：范围文档是否真实存在且可读，没实地读到就填 false<br/>- `unconfirmedAssumptions[]`：第 3 章状态列仍为「⬜ 待人工确认」的条目，格式为"主体：假设"<br/>- `scopeConfirmedBy` / `scopeConfirmedAt`：签字栏原文，仍是"（待填写）"或空白一律返回空字符串<br/>- `scopeSummary`：范围文档要点摘要<br/>- `summary`：**五段**上下文摘要（不超过 1200 字）：①审计范围与信任假设要点 ②已知不变量要点 ③已确认误报要点 ④已豁免问题要点 ⑤经济模型/资金流转要点 | 以前这一步输出的是一段纯文本，现在改成结构化 JSON，是因为下一步的门禁要靠 `unconfirmedAssumptions`、`scopeConfirmedBy` 这些字段做**纯代码判断**——判断依据必须是可被代码检查的字段，不能是一段"看起来像是确认过了"的自然语言。<br/><br/>另外，如果 `.audit/scope.md` 第 4 章已经写明了经济模型，这里直接采信、不再重复去翻 PRD 文档；那一章本来就是人工签过字的权威出处，重新翻一遍既费 token 又可能得出跟签字版本不一致的说法 |
| 1.2 | 范围文档门禁 | 无（纯函数） | 用 `evaluateScopeGate(context)` 判三条硬性条件：文件存在 → 没有剩余「⬜ 待人工确认」→ 签字栏确认人与确认日期都非空。任一不满足就打印每一条卡住的原因并早退，返回 `{ error: '审计范围文档未就绪', scopeGate }` | 这道门禁必须是纯代码，不能交给 LLM 判断——让 AI 来评估"我的前置条件是不是满足了"，等于让它给自己开考勤。而且是 fail-closed：上下文返回空值或结构异常时一律不通过，因为"读不出来"和"确认过了"是两回事。<br/><br/>为什么值得为此挡住整条流水线：L2 判断"代码行为 ≠ 业务意图"的能力完全取决于它知不知道业务意图；没有经人工签字的信任假设，它只能报模式化漏洞，还会把设计上允许的管理员操作误报成漏洞 |
| 1.3 | 自动发现审计目标 | 无 | 把 `contracts/` 目录翻一遍，找出核心合约（测试代码、mock、library 这些不算） | 不想让用户每次审计都得手动把全部合约文件列出来；顺便把测试代码/mock/纯接口这些排除掉，让审计精力都花在真正管钱、管资产逻辑的代码上 |
| 1.4 | 初始化 `.audit/` 目录结构 | 无 | 创建 `.audit/invariants.md`、`.audit/false-positives.md` 这些配置文件（如果还没有的话） | L1 到 L4 后面各阶段都要读写这些文件（误报库、豁免库、报告目录等），第一次跑的时候要是这些文件不存在，后面读取就会失败；提前把架子搭好，保证流程能从零开始顺利跑通 |
| 1.5 | 加载已知误报与豁免 | 无 | 读一下 `.audit/false-positives.md` 和 `.audit/exemptions.md`，给后面 L2 阶段降噪用 | 没有这层降噪的话，同一条已经被人工确认是误报、或者已经书面豁免的问题，会在每一轮审计里被反复报出来，白白浪费人工复核的精力，还会把真正的新发现淹没在旧噪音里 |

**门禁没过会看到什么**：

```
⛔ 审计范围文档未就绪，本轮审计不启动：
.audit/scope.md 中仍有 2 条信任假设为「⬜ 待人工确认」，请逐条核对后改成「✅ 已确认」：
  - owner：假定不作恶，且不会把 oracle 换成受控合约抽干资金池
  - Chainlink ETH/USD 预言机：假定喂价及时且准确，不会长时间停更
.audit/scope.md 文末签字栏的「确认人」为空，未完成人工签字
```

处理办法只有一个：去把 `.audit/scope.md` 签完。怎么签见 [generate-scope-guide.md](./generate-scope-guide.md)。

#### **L1 阶段 - 静态扫描**

| 步骤 | 操作 | 工具 | 说明 | 为什么需要 |
|------|------|------|------|------|
| 2.1 | 工具可用性检测 | `slither` 或 `aderyn` | 看看 slither 或 aderyn 装没装（没装就自动试着装） | 工具要是装不上，必须老实标出来，不能悄悄跳过——不然会让人误以为"L1 扫过了、没发现问题"，实际上压根就没跑起来 |
| 2.2 | 运行确定性扫描 | **slither** 或 **aderyn** | 把所有目标合约过一遍静态分析，查重入、权限问题、整数溢出、没初始化的变量这些 | 静态工具靠固定规则，能可靠、低成本地抓住那些"套路很明确"的问题，把这类基础问题挡在 L2 语义审计前面，让更贵的 LLM 审计专心去啃工具查不出来的语义/业务逻辑问题 |
| 2.3 | 结果收集与聚合 | 无 | 把各个工具的输出合并起来，按严重度（Critical/High/Medium/Low/Info）分类 | 几个工具输出格式都不一样，得先统一到同一套严重度分级下，后面判门禁（比如 High 是不是清零了）才有个统一的标准 |
| 2.4 | 误报过滤 | 无 | 跟 `.audit/false-positives.md` 对一下，把已知的误报去掉 | 静态工具靠死规则，天生就会有误报（比如明明加了 nonReentrant 还是被报重入）；不过滤的话会把 High/Medium 计数污染掉，直接影响门禁判断准不准 |
| 2.5 | 生成 L1 原始报告 | 无 | 输出成 `.audit/reports/slither-report.json` 或者类似格式 | 给 L2 阶段提供"哪些套路已经被工具认领了"的背景信息，避免语义审计再把同一类已知问题重复报一遍，让它把精力放在"代码写的和业务想的对不对得上"这种工具做不到的判断上 |

**L1 产出**：一份确定性发现清单（可信度高）

#### **L2 阶段 - LLM 语义审计**

| 步骤 | 操作 | 工具 | 说明 | 为什么需要 |
|------|------|------|------|------|
| 3.1 | 合约源码加载 | 无 | 把目标合约完整的 Solidity 代码读进来 | 语义审计得照着真实源码逐行判断，不能只靠 L1 那份结构化摘要去二次总结，不然会把 L1 的盲区也一起继承过来 |
| 3.2 | 四角色对抗审计 | **Claude LLM** | 🔵审计员 → 🔴攻击者 → 🟢修复工程师 → ⚖️裁判，一个角色接一个角色地分析。<br/>🔵审计员吃的是完整的五段上下文摘要；⚖️裁判**额外吃一份 `.audit/scope.md` 的要点摘要**（`scopeSummary`） | 让一个角色一次性搞定"发现+攻击路径+修复+定级"，很容易既当运动员又当裁判，自己骗自己；拆成四个角色、让裁判默认"每条发现都是错的，除非代码能逐行证明"，能把误报率明显压下去。<br/><br/>裁判之所以要多吃一份范围文档摘要：管理员能做某个操作到底算不算漏洞，完全取决于信任假设，而裁判正是做这个取舍的角色 |
| 3.2.1 | 裁判规则第 0 条：用信任假设过滤 | **Claude LLM** | 裁判在逐条走查源码之前，先拿已签字确认的信任假设过一遍：<br/>- 一条发现的攻击前提**正是**某条已确认的信任假设（典型如"owner 能调 `setFee` 抽走手续费"，而范围文档已确认 owner 是可信多签）→ 移入 `rejectedFindings`，并**写明命中了哪一条假设**；<br/>- 攻击路径**不依赖**任何被信任的主体（任意外部账户就能发起）→ 信任假设不构成拒绝理由，继续按后面的规则走查；<br/>- 特别注意："信任 owner"只覆盖 owner 的**合法操作**，**不覆盖**"任意人都能冒充 owner"这类权限校验缺陷 | 没有这条规则，报告里会塞满"owner 权限过大"这种在本项目设计上就成立、且已经被人签字接受的条目，把真正的问题淹掉。<br/><br/>而后半段的限制同样重要：如果把"我们信任 owner"扩大解释成"跟 owner 沾边的都不是漏洞"，那么"权限校验写漏了、任何人都能当 owner"这种最致命的缺陷反而会被这条规则一笔勾销——所以拒绝理由必须落到"命中了哪一条假设"上，写不出来就不能拒 |
| 3.3 | 10 大专项类别分析 | **Claude LLM** | 重入、访问控制、精度、预言机、业务逻辑这些专项，一类一类深入分析 | 一次性让模型审计"所有漏洞类型"，注意力容易分散、冷门风险容易漏掉；按专项拆开、每次只用一个窄提示词盯一类，误报率能降 60%+，同时还能把经济模型、升级治理这类静态工具查不出来的语义风险也覆盖到 |
| 3.4 | 结果去重与合并 | **Claude LLM** | 把重复的发现挑出来合并、去掉已知的误报 | 好几个专项类别的候选发现可能其实指向同一处代码问题，不去重的话同一个漏洞会在报告里反复出现，误导人工复核对问题数量和工作量的判断 |
| 3.5 | 标记需要 PoC 验证的项 | 无 | 看发现的确定程度，标出哪些得进 L3 | 语义审计的"疑似发现"还停留在推理层面，不代表真能被利用；只有那些"得靠运行时状态才能确证"的才值得投入 L3 的成本去验证，能靠代码逐行证明的就不用再重复验证了 |

**L2 产出**：一份语义级发现清单（可信度中等）

#### **L3 阶段 - PoC 复现验证**

| 步骤 | 操作 | 工具 | 说明 | 为什么需要 |
|------|------|------|------|------|
| 4.1 | 收集待验证发现 | 无 | 把 L2 里标了"需要验证"的发现挑出来 | L3 做 PoC 的成本不低（每条最多 5 轮 agent loop），只对 Critical/High 且需要证据的发现砸验证资源，别在低优先级、或者已经能靠代码证明的东西上浪费 |
| 4.2 | PoC 生成 | **Claude LLM** | 写一份能跑起来的 Hardhat 测试代码 | "疑似"和"确认"之间就差一条线——能不能拿真实可运行的测试代码把攻击效果复现出来；没有能跑的 PoC，攻击路径写得再合理也只是猜测 |
| 4.3 | PoC 执行与验证 | **Hardhat** | 真的把 PoC 跑一遍，记录跑出来的结果 | 必须真的跑一遍拿到执行反馈（状态差分/断言输出），不能让模型自己"觉得"测试会过——这是把"疑似漏洞"升级成"确认漏洞"唯一站得住脚的证据来源 |
| 4.4 | 验证结果分类 | 无 | 分成 Confirmed / Invalid / Inconclusive | 严格区分状态，防止把"迭代次数用完了还是没证明成立"的发现悄悄升级成 Confirmed，误导门禁判断和人工复核该先看哪个 |
| 4.5 | 反例永久保存 | 无 | 把验证成立的 PoC 存进 `.audit/regression/`，当回归测试用 | 确认成立的 PoC 沉淀成回归测试之后，以后修复这个问题时可以直接拿它验证修好了没有，也防止同一个漏洞在后续改动里又被不小心带回来 |

**L3 产出**：一份 PoC 验证报告（里面是已经验证成立的发现）

#### **L4 阶段 - 复核与归档**

| 步骤 | 操作 | 工具 | 说明 | 为什么需要 |
|------|------|------|------|------|
| 5.1 | 汇总审计发现 | 无 | 把 L1/L2/L3 的发现全部收集起来，按合约分组 | L1/L2/L3 出来的东西格式和粒度都不一样，得先按合约统一汇总，才能整理出一份连贯的复核材料，不然人工得分头去看三份互相不搭边的原始输出 |
| 5.2 | 生成人工复核清单 | **Claude LLM** | 给每条发现打一个复核清单标签（必须修复/建议修复/可接受/需人工判断） | AI 能看出代码层面的问题，但"经济模型的假设站不站得住""多签权限是不是真的分散在不同人手里""升级路径能不能回退"这类"结构性做不到"的判断必须交给人；清单的作用就是精准指出"人还需要确认哪些事"，不是替人下最终结论 |
| 5.3 | 记录豁免决策 | 无 | 对能接受的风险项，查一下有没有书面豁免记录 | 有些已知风险是业务上主动接受的（比如测试网阶段管理员权限比较集中），不核对书面豁免记录的话，同一个问题会在每一轮审计里被反复当成新发现报出来 |
| 5.4 | 生成总报告 | 无 | 生成 `.audit/reports/audit-latest.md`（门禁、概览、发现、PoC、复核清单、元信息都在里面）。<br/>「审查元信息」表里有一行专门记范围文档：<br/>`\| 审计范围文档 \| .audit/scope.md（确认人：X，确认日期：Y） \|`<br/>确认人/确认日期缺失时显示"未提供" | 门禁结论、发现明细、PoC 证据、复核清单要是散在好几个地方，人工复核的时候得来回切换、容易漏看；汇总成一份结构化总报告，审计流程才真正能被交付业务测试/上线决策采信。<br/><br/>范围文档那一行是为了**可追溯性**：这轮审计的结论建立在一组信任假设之上，半年后回过头问"上线时那版范围文档是谁签的字"，报告里直接能查到，不用去翻 git 记录猜 |
| 5.5 | 报告写入磁盘 | 无 | 覆盖写入 `.audit/reports/audit-latest.md` | 固定路径覆盖写入，配上长度核对这道纯代码校验，是防"LLM 说自己写成功了，实际内容被截断/被概括"这类系统性风险的最后一道保险 |

**L4 产出**：一份完整的审计总报告 + 复核清单（AI 只负责产出，最终决策还是人来定）

**关键原则**：
- L4 出来的是一份"复核清单"，**不是拍板结论**
- 误报要不要入库、要不要书面豁免、测试能不能放行，这些都必须**人来签字**
- 这些决策 AI 不会替你签

## 4. formal-verification-halmos（形式化验证）

### 概述

**这是干嘛的**：对人工指定的"核心数学模块"（比如 AMM 定价曲线、清算计算、份额舍入这些）做有界的符号执行，在划定的边界里把数学正确性穷举验证一遍。

**能证明到什么程度**：⭐⭐⭐⭐⭐ 高——在给定的边界内是穷举验证过的，但前提是得把边界老实说清楚。

**跑一次贵不贵**：偏高，符号执行可能跑得很慢。

**大概要多久**：一般 10-30 分钟，看函数复不复杂、loopBound 设多大。

**有一点必须说清楚**：Halmos 的证明是**有前提的**——"在划定的边界内没找到反例"，不等于"这东西绝对安全"

### 工作流程与步骤

#### **准备阶段**
| 步骤 | 操作 | 工具 | 说明 | 为什么需要 |
|------|------|------|------|------|
| 1.1 | 验证 modules 参数 | 无 | 确认用户是不是显式指定了 `modules`（必填，不给就直接报错） | 形式化验证不便宜（符号执行可能跑得很慢），而且只对"核心数学模块"才划算；要是让它自动去找目标，会把证明资源浪费在一堆不值得穷举验证的普通业务合约上，所以干脆要求人来判断、显式指定，不做自动发现 |
| 1.2 | 加载目标源码 | 无 | 把指定模块的 Solidity 代码读进来 | 证明得照着真实的函数实现来，不能凭空猜数学语义 |
| 1.3 | 识别核心函数 | **Claude LLM** | 照着 `focus` 描述，定位出要证明的函数 | 用户给的 focus 通常就一句话（比如"份额舍入精度"），得先把它拆解、定位到具体函数，才能设计出有针对性的证明装置 |
| 1.4 | 记录证明边界 | 无 | 根据 `loopBound` 和用户的说明，把这次验证的边界假设记下来 | Halmos 的证明是有前提的——"给定边界内没找到反例"不等于"绝对安全"；得提前把边界假设记清楚，不然后面报告很容易把"在有限边界内成立"包装成"绝对安全" |

---

#### **规格设计阶段**

| 步骤 | 操作 | 工具 | 说明 | 为什么需要 |
|------|------|------|------|------|
| 2.1 | 分析函数数学语义 | **Claude LLM** | 搞清楚函数的数学含义、输入有什么约束、输出跟输入什么关系、边界情况是什么样 | 只有先弄明白函数真正要保证的数学关系（单调性、守恒、边界）是什么，才能设计出真正验证这条性质的断言，不是随便写几个 assert 凑数 |
| 2.2 | 设计形式化规格 | **Claude LLM** | 用自然语言或者半形式化的语言，把要验证的性质写出来（PRE/POST/不变量） | 把"这个函数应该长啥样"这种模糊描述，转成能写进 Solidity assert 里的精确 PRE/POST 条件，这是符号执行能自动化验证的前提 |
| 2.3 | 设计测试装置 | **Claude LLM** | 生成 Solidity 代码：符号化的 wrapper + 前置条件 + assert 语句 + Halmos 的钩子 | Halmos 得有一个能编译的 Solidity 装置（符号变量 + vm.assume 约束 + assert）才能做符号执行；装置写得好不好，直接决定证明的边界是不是真反映了业务约束，而不是为了让证明"好过"而故意把范围收窄 |

**规格设计产出**：一份形式化规格 + 一套 Halmos 认的 Solidity 测试装置

#### **Halmos 证明阶段**

| 步骤 | 操作 | 工具 | 说明 | 为什么需要 |
|------|------|------|------|------|
| 3.1 | 工具可用性检测 | `halmos` | 看看 halmos 装没装（没装就自动试着装） | 跟其他工作流一个原则——装不上就老实报 ToolUnavailable，绝不伪造证明结果 |
| 3.2 | 编译装置代码 | **Hardhat** | 把 Solidity 装置代码编译成字节码 | 符号执行是在字节码层面跑的，装置代码写完得先能正常编译，不然 Halmos 根本无从下手 |
| 3.3 | 启动 Halmos 符号执行 | **Halmos** | 跑 Halmos：把所有路径都符号执行一遍 → 检查 assert → 违反了就把反例收集下来 | 这是唯一能在给定边界内把所有执行路径都穷举一遍的办法——普通测试用例只能验证"这几个具体输入下成立"，符号执行能验证"边界内所有可能输入都成立"，证明力度比普通单测或 fuzz 高得多 |
| 3.4 | 处理验证结果 | 无 | 分成 Proved / Counterexample / Inconclusive / ToolUnavailable 四种 | 必须严格三分，尤其是求解器超时这种"没证出来"的情况，绝对不能被包装成 Proved，不然会给人一种错误的安全感 |
| 3.5 | 反例分析与记录 | **Claude LLM** | 碰到 Counterexample，就写一段人话说明（触发条件、为什么违反、有什么风险、怎么修） | Halmos 输出的原始反例通常就是一堆具体数值，不好直接看懂业务上意味着什么；转成人话说明之后，工程师才能真正拿去定位和修复问题 |

**Halmos 证明产出**：每个函数一条证明结果（Proved/Counterexample/Inconclusive）

#### **结果汇总阶段**

| 步骤 | 操作 | 工具 | 说明 | 为什么需要 |
|------|------|------|------|------|
| 4.1 | 收集所有模块的证明结果 | 无 | 把这次验证的所有函数结果汇总起来 | 一个模块可能有好几条独立性质的证明结果，得先按模块归总，才能整出一份有意义的模块级摘要 |
| 4.2 | 识别阻断项 | 无 | Counterexample 项 = **阻断项**（表示发现了数学错误，必须修复） | Counterexample 说明已经找到了具体的数学错误（不是猜的），这是优先级最高、必须先修的问题，得在报告里显眼标出来，不能跟 Proved/Inconclusive 混在一起被埋没 |
| 4.3 | 验证假设完整性 | **Claude LLM** | 检查证明里用到的所有假设是不是都老老实实记下来了 | 证明可不可信，全看边界假设有没有诚实、完整地记下来；要是漏了一条假设，看报告的人可能会误以为证明覆盖的范围比实际更大 |
| 4.4 | 生成验证报告 | 无 | 生成 `.audit/reports/halmos-verification-latest.md`（参数、概览、阻断项、边界假设、逐模块明细、诚实声明都在里面） | 把每个函数的证明结果、边界假设、反例整理成结构化报告，这样"数学级别的证明结论"才能被不是搞形式化验证出身的审计人员看懂、采信 |
| 4.5 | 报告写入磁盘 | 无 | 覆盖写入 `.audit/reports/halmos-verification-latest.md` | 固定路径覆盖写入 + 长度核对，防止归档过程里内容被截断/被概括，出现"报告说已经证明了，实际内容却缺了一块"这种坑 |

## 总结对比

| 工作流 | 干的是什么 | 大概要多久 | 靠谱程度 | 什么时候用 |
|--------|--------|---------|--------|--------|
| **generate-scope-template** | 代码分析 + LLM 识别（范围/角色/信任假设/资金流） | 3-8 分钟 | N/A | 所有流程的起点；跑审计流水线之前的硬前置 |
| **generate-invariants-template** | 代码分析 + LLM 识别 | 2-5 分钟 | N/A | 项目刚起步，第一次跑 fuzz 之前 |
| **invariant-fuzz-campaign** | 随机测试 + 抽样覆盖 | 5-20 分钟 | ⭐ 低 | 核心逻辑改完之后，隔一段时间跑一次 |
| **smart-contract-audit-pipeline** | L1 静态扫描 + L2 LLM 审计 + L3 PoC | 5-15 分钟 | ⭐⭐⭐ 中 | 默认入口，每次审计前都跑（需 scope.md 已签字） |
| **formal-verification-halmos** | 符号执行 + 穷举验证 | 10-30 分钟 | ⭐⭐⭐⭐⭐ 高 | 数学模块需要严格证明时，手动触发 |

### 建议工作流用法顺序

**完整顺序**：
```
generate-scope-template
   ↓ （👤 人工逐条签字 .audit/scope.md —— 不签字下一步跑不了）
generate-invariants-template
   ↓ （👤 人工看一遍、改一改 .audit/invariants.md）
smart-contract-audit-pipeline
   ↓ （把发现的问题修掉）
invariant-fuzz-campaign
   ↓
formal-verification-halmos
```

**首次使用（项目初期）**：
```
1. generate-scope-template       ← 先划清范围、把信任假设摆出来
   ↓ （人工逐条把 ⬜ 待人工确认 改成 ✅ 已确认，填写签字栏）
2. generate-invariants-template  ← 再生成一份不变量清单
   ↓ （人工看一遍、改一改 .audit/invariants.md）
3. smart-contract-audit-pipeline ← 跑一遍 L1-L4 完整审计
   ↓ （把发现的问题修掉）
4. invariant-fuzz-campaign       ← 跑深度 fuzz，验证不变量
```

**常规迭代**：
```
- 代码改完 → smart-contract-audit-pipeline（快速过一遍）
- 角色/权限/经济模型有变化 → generate-scope-template 重跑 + 重新签字
- 核心逻辑改动大 → invariant-fuzz-campaign（fuzz 验证）
- 数学模块改动 → formal-verification-halmos（得自己指定 modules）
```

## 关键原则总结

1. **五个工作流是互补关系**，不是谁能替代谁
2. **AI 出的都是辅助结果**，最终拍板必须是人
3. **信任假设必须人签字**，AI 生成的一律标「⬜ 待人工确认」，包括那些从代码直接推断出来的；`smart-contract-audit-pipeline` 会硬性拦住没签字的情况，没有参数能绕过
4. **Halmos "没找到反例" ≠ "绝对安全"**，边界必须写清楚
5. **工具装不上不会硬编结果**，会老实说"不可用"
6. **所有产出物都放在 `.audit/` 目录下**，方便以后翻和复用
